## 五、本轮发现并修复的数据损坏缺陷（最重要）

### 编码语义混合 → 静默改写文件（已实测复现）

```
UTF-8 文件「中文内容测试」
  → 用户切到 GBK"看一眼"（界面显示乱码「涓�鏂囧唴瀹规祴璇�」）
  → 顺手按 Ctrl+S
  → 磁盘被改写！

     原字节: b'\xe4\xb8\xad\xe6\x96\x87\xe5\x86\x85...'   中文内容测试
     新字节: b'\xe4\xb8?\xe6\x96\x87\xe5\x86\x85...'      读回 '�?文内容测�?'
```

**不保存则无损**（关闭重开正常）—— 危险恰恰藏在"看一眼 + 保存"这个最自然的动作里。

**根因**：`change_encoding` 把 Notepad++ 明确区分的两种语义混成一个动作：
"Character sets 改解释"（文本语义变、字节不变）与 "Convert to 编码"（字节变、文本不变）。

**本轮修复**：
* `Document.change_encoding(mode=..., require_lossless=...)` 显式区分两种语义；
* 新增 `Document.would_lose_text(encoding)` 判定（含**"当前已是乱码则本次属修正、不拦截"**的例外）；
* 状态栏切换走 **fail-closed**：有损时弹确认框并明确告知"保存会改写文件"，取消则不切换；
* 实测四种场景全部正确：真损坏被拦、有损修正放行、纯 ASCII 放行、误判编码修正放行。

## 七、明确"不该做"的事

| 不做 | 理由 |
|---|---|
| 补齐 ~50 种字符集 | 目标用户是中文程序员，现有 13 项已覆盖 GBK/GB18030/Big5/UTF-8/UTF-16/Shift-JIS/EUC-KR |
| 复刻 Notepad++ Run `$()` 变量 DSL | 正解是接线已有的 `core/project_tasks.py` + 任务面板 |
| Windows Shell 右键集成 | 需写 HKCR/卸载残留/UAC，与"便携优先"取向冲突 |
| 打印/打印预览 | 2020s 代码编辑器的死功能；要交付文档应做 Markdown→PDF |
| 十六进制/拼写检查/列对齐 | 应由插件生态承接，不进核心 |
| 可视化 UDL 编辑器 | 巨大工程；更该做 `.editorconfig` + 项目配置（`core/project_config.py` 已存在） |
| 追赶 155 个插件的规模 | 生态只能长不能补；应打磨"第三方 30 分钟能上架" |
| **为对标而稀释 AI/LSP/调试/Git** | 青草全部 8 项"更优"都在这条线上；照 N++ 清单补齐只会得到"更差的 Notepad++" |

## 八、下一步建议（按投入产出比）

1. **先做 P0 的 11 项**（合计约 2-3 天）：把已有引擎交付出去。其中 P0-1/P0-2/P0-3
   是**明确的缺陷**（宏录不到、草稿捞不回、全局替换错替换），不是"缺功能"。
2. **P1-7 入口重排**（0.5-1 天）：让用户**找得到** LSP/调试/Git/AI —— 目前它们
   分散在插件注册路径里，试用者很容易以为"这编辑器什么都没有"。
3. **P1-5/P1-6 离线能力兜底**：LSP 默认关闭 + 无静态词表 = 没装服务器的语言上
   补全体验**弱于 Notepad++**，这是差异化叙事最容易被戳破的一点。
4. **P0-11 门禁改造**：把"未接线"从"可豁免基线"改为"必须递减"，否则孤立模块
   只会继续累积（当前 30 个 / 9,200 行）。
