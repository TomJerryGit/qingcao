## 一、实时协作 —— **决策：删除（方案 C）**

### 原来的事实

| 项 | 状态 |
|---|---|
| 协议 | 裸 TCP（`socket.AF_INET, SOCK_STREAM`） |
| 监听 | `bind(('0.0.0.0', 52000))` —— 监听所有网卡 |
| 加密 | **无** |
| 认证 | **无** |
| NAT 穿透 | **无** |
| UI | 完整（启动主机 / 加入 / 离开） |

### 为什么删除而不是接线

* **安全性**：接上 UI 就等于把"局域网内任意人可加入的无密码共享编辑端口"
  暴露给用户，且用户看不出风险；
* **可达性**：真实用户大多不在同一局域网，只做局域网等于功能半残；
* **无法验证**：本环境无网络，连"双端联调"都做不到，
  任何"已接线"的声明都不可信；
* **保留一半的代价**：只删 UI 留协议层，会留下"看得见代码但用不了"的债。

要做得先补：加密（TLS/端到端）、认证（邀请令牌）、
可达性（中继或 WebRTC）、冲突语义、真实联调环境 —— 属独立立项。

## 二、代码片段市场 —— **决策：改造为本地片段包库（方案 B）**

### 原来的事实

```python
MARKET_API = "https://api.github.com/repos/qingcao-editor/snippets/contents"
```

**实测 HTTP 404**（`{"message":"Not Found"}`）—— 仓库不存在。
即使接上 UI，点"刷新"也只会显示 4 条硬编码示例，"市场"是假的。

### 改造后

* 后端 `core/snippet_market.py` 重写为 `SnippetLibrary`：
  扫描**本地片段包目录**（默认 `<应用根>/data/snippet_packs`，可自选）；
* 片段包格式简单、可手写、可版本控制：
  `{"snippets": [{"name","language","description","body"}]}` 或裸数组；
* 入口：**工具 → 📚 代码片段库…**；
* 「导入选中」把片段登记进本地 `SnippetManager`（**纯本地写入**）；
* 目录为空时展示**内置示例**（让用户知道片段包长什么样）；
* 保留原 `SnippetMarketClient` 类名别名，避免外部 import 断裂。

### 顺手修的相关缺陷

`core/snippets.py` 的存储路径原为相对路径 `"snippets.json"` ——
打包后从快捷方式启动会写到 `C:\snippets.json`，换目录启动就读不到，
用户导入的片段"消失"。已改为从 `app_root_dir()` 派生绝对路径
（与 `Document._draft_dir` / `crash_stats.CRASH_DIR` /
`snapshot.SNAPSHOT_DIR` 同一模式 —— 这是本仓库反复出现的同类缺陷）。

### 额外改进

* 同名不同内容的片段导入时**自动加 `_2` 后缀**，不静默覆盖已有片段；
* 无 `body` 的片段被拒绝（不会往库里塞空片段）；
* 片段包目录选择被记住（`QSettings: snippet_pack_dir`）。

## 四、如果将来想重新做这两件事

### 实时协作

参考实现已删除，但技术方案可参考以下顺序：
1. 先定**安全模型**（加密 + 认证）再写代码，不要先做连通性；
2. 优先考虑 CRDT/OT 库而非手写 Insert/Delete 消息；
3. 至少要有两台真实机器的联调环境，否则不要宣称"可用"。

### 片段市场（网络版）

若真要做联网市场：
* 需要一个**真实存在**的内容服务（自建 API 或真实存在的 GitHub 仓库）；
* 必须做**内容审核**与**代码信任提示**（下载并执行他人代码有风险）；
* 建议先在本地库形态上积累用户，再考虑联网。
